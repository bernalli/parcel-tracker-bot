# Internationalisation

The bot and the web dashboard ship in English and Italian, and each user picks
a language with `/lang` (or in the dashboard settings). Adding a language is a
self-contained `.po` file plus a PR.

## Architecture

- Library: stdlib `gettext` + `babel` for extraction; one catalog serves the
  bot (Python, `_()` / `_n()`) and the dashboard (Jinja templates, `_()` /
  `ngettext()`).
- Source language (`msgid`): English. We translate from English into other locales.
- Locale tree: `src/parcel_tracker/i18n/locale/<lang>/LC_MESSAGES/messages.po`.
- Compiled `.mo` files are produced at build time (Docker stage) — they are **not** committed.
- Per-user persistence: the `user_language` table (works for the owner and `ALLOWED_USER_IDS` too).
  Users who never chose follow `DEFAULT_LANGUAGE` (default `en`).
- The language is applied per update and per outgoing notification (a `ContextVar`), so one
  user's choice never changes what other users see.
- Telegram `language_code` from updates is **not** used by default for privacy. A user must
  opt in with `/lang it`.
- Public tracking pages follow the visitor's browser (`Accept-Language`).

## Switching language at runtime

In Telegram:

```
/lang en    # English (default)
/lang it    # Italiano
/lang       # show current language and available locales
```

The bot stores the choice in the SQLite DB and uses it for every future reply and
notification to that user only.

## Adding a new language

Example: Spanish (`es`).

```bash
python scripts/i18n.py init es          # creates locale/es/LC_MESSAGES/messages.po
python scripts/i18n.py missing es > todo.json
# translate the values in todo.json (keep keys untouched), then:
python scripts/i18n.py apply es todo.json
python -m parcel_tracker.i18n.build     # compile .mo files
pytest tests/unit/i18n tests/unit/web
```

Add the language name to `LANGUAGE_NAMES` in `src/parcel_tracker/web/render.py`
and to `_LOCALE_LABELS` in `src/parcel_tracker/bot/keyboards.py`, then open a
PR with the new `.po` file. `.mo` files are built in CI and in the Docker image.

## Re-extracting strings after code changes

After adding or changing a user-facing string:

```bash
python scripts/i18n.py update      # re-extract, merge into every .po, drop removed strings
python scripts/i18n.py missing it  # what still needs an Italian translation
```

`tests/unit/i18n/test_catalog_sync.py` fails when the template is out of date,
when a catalog keeps strings the code no longer uses, or when Italian misses a
translation.

## Plurals

Use `ngettext` (already imported as `_n`) for any string that can be plural:

```python
from parcel_tracker.i18n import _n

await update.message.reply_text(
    _n(
        "{count} parcel updated",
        "{count} parcels updated",
        n=count,
    ).format(count=count),
)
```

## Style guide for translators

- Keep emoji in place (they convey status colour at a glance).
- Keep HTML tags (`<b>`, `<code>`) verbatim — the Telegram client renders them.
- Keep placeholders verbatim: `{tracking_number}` in bot strings (`str.format`) and
  `%(name)s` / `%(num)d` in dashboard strings (Jinja gettext).
- Match the politeness register of the source: the English baseline uses second-person
  imperative for commands ("Add a parcel", not "Please add a parcel"). Translate accordingly.
